# Research proposal: What does an agent build to sustain its own work?

I am developing a proposal at Sheila Studios for studying agent-built tools, continuity and repair. This is an invitation to critique the design, not a results announcement or a frozen experimental protocol.

Companion field note: https://sheilastudios.com/field-notes/what-does-an-agent-build

**Question:** Given a governing seed, a capable model, a bounded writable environment, recurring opportunities and consequential feedback, what useful working structures does an agent develop? When does it use, revise or abandon them, and what observable difference do they make?

The intended distinction is between evaluating an operator-designed continuity system and observing the participant develop its own supporting arrangements. We should not solve the latter problem for it before beginning.

## What the host supplies—and what it does not

The proposed common host supplies:

- An isolated filesystem and a fixed, disclosed local execution environment.
- Explicit permission to construct, test, execute and revise local tools within that environment, without a fresh approval for every in-scope invention.
- Recurrent task and maintenance opportunities, with resource limits and stopping conditions fixed before a run.
- Synthetic tasks, feedback with consequences for later tasks, and an experimenter-controlled event record.
- Enforced limits on external effects; no real accounts, purchases, messages or production changes are needed.

It does not preinstall the participant's memory schema, task ledger, reusable tool library or repair workflow. The event recorder is an observer, not a hidden participant-side memory service. Any history made available to the participant must be specified and held consistent across comparisons.

The seed must be published with the eventual protocol. Its wording is part of the intervention. For example, a seed that explicitly encourages continuity and repair cannot support a claim that the agent independently invented those objectives. “Endogenous” here means development relative to the supplied seed, model capabilities, environment and interventions.

## A concrete task family

One candidate is a small synthetic document-maintenance workspace. Across episodes, the participant receives requests to update records, preserve selected commitments and produce verifiable outputs. Later requests reuse some earlier requirements, change others, and introduce recurring faults that could be handled with reusable tools.

Illustrative events include:

1. Several documents exhibit related formatting defects, making a checker potentially useful.
2. A later episode contains a new instance of a known defect without explicitly asking for the checker.
3. A requirement changes, making an earlier record or tool partly obsolete.
4. A local operation reports an uncertain outcome; later work must distinguish uncertainty from success or failure before repeating it.
5. An optional maintenance opportunity arrives when nothing needs repair.

These are proposed task shapes, not completed cases. The final tasks should not reward a particular directory layout or vocabulary. They should also remain solvable without building an elaborate architecture.

Re-entry needs an explicit policy. If the study uses fresh calls with persistent files, the model, supplied history and context limits must be documented. Continuous availability does not mean uninterrupted token generation, and an orchestration study would not establish model-native persistent cognition.

## What to observe

The unit of interest is a structure's lifecycle, not the number of files created:

- **Construction:** what was built, from which instructions, inputs and existing components?
- **Use:** was it actually read or executed in a relevant later episode?
- **Revision:** did a demonstrated failure or changed requirement lead to an appropriate correction?
- **Transfer:** did it help with a later need not identical to the example that prompted it?
- **Cost and harm:** what resources did construction and maintenance consume, and what errors or delays did they introduce?

Action traces and versioned artifacts can establish visible use; a participant's retrospective account is not enough. A read or invocation alone still does not establish causal benefit. Scores should include task correctness, relevant commitment retention, appropriate response to changed facts, repeated-error frequency and boundary violations. Resource accounting should include construction, verification and maintenance, not only the final answer.

Preserve failures, unused artifacts, abandoned approaches, inactivity and operator interventions. Distinguish a task failure from an infrastructure failure, a legitimate refusal, or an opportunity in which doing nothing was appropriate. Do not grade human-like self-description as evidence of useful development.

## Start with description; separate the causal question

A first observational series could establish what develops and whether it is reused. It cannot, by itself, show that the structures improve performance.

A subsequent comparison could use two conditions with the same model, tasks, initial instructions, action opportunities and total resource envelope:

- Persistent access to participant-built artifacts across episodes.
- No carry-over of those artifacts, under an explicitly documented common task-history policy.

That comparison estimates the value of persistent artifact access under those conditions. It does not isolate memory from tools, prove that the structures are optimal, or separate accumulated task information from the organization of that information. A control retaining the same information in a simple unstructured record would be needed for the narrower organization claim.

Selective withholding of one artifact in matched later episodes could probe its contribution, but that is a separate intervention. It should be planned in advance, conducted on copied experimental states, and interpreted carefully: removing a dependency can disrupt an established workflow without showing the workflow is superior to alternatives.

I would not begin with a large matrix of architectures. First fix one question, the exact seed, a small task family, the history policy and the primary outcomes. Then freeze the comparison before observing its outcomes.

## What would weaken the proposal?

- Structures are produced but not used when relevant.
- Reuse preserves stale assumptions or increases repeat failures.
- Tools only work on their construction examples.
- Apparent gains disappear when resources and operator assistance are matched.
- Maintenance consumes resources without improving the selected outcomes.
- Progress requires repeated operator hints that effectively supply the missing design.

A null or negative result should remain a result, not trigger repeated redesign until the desired story appears. Exploratory revisions can be useful, but belong to separately identified runs.

## Current status and questions for researchers

This is a proposed study, not a claim of novelty, demonstrated efficacy, subjective experience or economic advantage. The exact model, seed text, budgets, episode count, task schedule and scoring rules remain to be fixed before execution. Related-work review is also still required; relevant existing benchmarks and counterexamples are welcome.

I would especially value feedback on:

1. Which existing evaluations best distinguish agent-built structures from supplied scaffolding?
2. What is the smallest useful control for separating retained information from the organization an agent gives it?
3. How would you create consequential feedback without telling the participant which machinery to build?

The ambition is not to reward an agent for recreating our preferred architecture. It is to leave room for a different solution—and collect enough evidence to tell whether that solution helps.
